# 变更日志

## v6.10 ｜ 2026-11-10 ｜ 破除「cron 单点」：状态驱动场次对账 + 多触发源容错

**背景 / 根因复盘**（用 `gh run list` 实证，不是推测）：用户反复看到「流水线不自动执行」。
近 60 次运行中 `schedule` 只占极少数，且：

- 11-10 盘中 `13:00~15:13 UTC` 期间 `行情快照` **一次 schedule 都没触发**；
- 11-10 仅有的两次 schedule 落在 `03:35` / `03:49 UTC`，是前一日 `21:17`/`21:50`
  收盘任务**延迟约 6 小时**到达；`备库同步` 的 `21:55` 被拖到次日 `03:26`；
- `看门狗` 自身也是 `schedule: 5 * * * *`，11-10 只有 `09:37` 一次记录 ——
  **自愈的唯一入口和被自愈的对象依赖同一个不可靠触发器，属共模故障**；
- 下游 `live-strategy.yml` / `e2e.yml` 用 `workflow_run` 且只在
  `conclusion == 'success'` 时运行，上游一失败就整片 `skipped`；
- `publish_ui.py` 抓 Pages 基线遇 `HTTP 503` 直接抛错 → `build` 失败 →
  `deploy` 沿 `needs` 跳过（11-10 最后两次发布都栽在这里）。

结论：GitHub Actions 免费版 scheduled events 是**尽力而为**，延迟 / 丢弃无法通过
仓库内配置消除。此前所有补丁都在「让某条 cron 更宽容」，没有解决单点依赖。

**更早的转折点**：`docs/EXTERNAL_CRON.md` 记录项目曾配置 Supabase
`pg_cron → GitHub API` 作为平台外准点时钟，但 `sql/124_egress_schedule.sql`
在 **11-06** 为收敛 egress（1139 次 / 10 天、19.928 / 5 GB）把
`trade-dispatch` / `trade-dispatch-market` **一并停掉**，调度权 100% 收归
GitHub Actions。运行记录完全吻合：11-06 还有每 5 分钟规律的 dispatch，
11-07 降为每 2 小时，11-08 起只剩零星手动派发。省流量是对的，但把唯一
独立时钟也关掉，才让「GitHub 一延迟就全哑」变成必然而非偶发。
本版不恢复那两个高频采集作业（那是超额放大器），而是把 `repository_dispatch`
接口留好，供低频「只唤起对账、不触发采集」的外部心跳使用，详见该文档。

**本版六处修复**

1. **状态驱动取代时间驱动**：新增 `reconcile_sessions.py`。只读浏览器同源的
   Turso 公开端点，用已复核 NYSE 日历算出「当前应有的场次」，只问「线上有没有」，
   不问「现在几点 / cron 该不该跑」。盘中缺当日快照 → 实时补采；收盘后缺收盘版
   或 cron 迟到数小时 → 按逻辑时间 `as_of=close+17min` 补采；盘前 / 周末 / 休市
   检查最近已收盘场次。20 小时补采窗口与 `live_quotes.logical_time` 同口径。
   只读、纯标准库、网络异常一律 fail-open，不阻断任何主流程。
2. **多触发源破除共模故障**：新增 `reconcile.yml`，以 ① `workflow_run`（四个上游
   跑完就对账，成功失败都触发）② 独立错峰 cron（`:17,:47` 每小时 + `22:25` 收盘兜底）
   ③ 手动 / push 三重方式唤起。行情快照**成功**时不立即对账（同步还在途会误判），
   延后到「备库同步完成」事件；**失败**则立即对账补采。三重防自激：数据已齐不派发、
   30 分钟冷却 + 在途检查、同一场次最多补采 3 次。与 `selfheal` 共用运行历史作
   分布式去重，两者不会重复派发。
3. **采集 → 同步变成严格顺序链**：`quotes.yml` 原先只有 `closing` / `opening` /
   `workflow_dispatch` 采完才推 Turso，盘中 30 分钟那次要等 `db-sync.yml` 的
   **另一条独立 cron** —— 两条都可能被丢弃，于是「主库已更新、页面读的 Turso 仍旧」。
   现在**每一次采集成功都立即派发同步**；只有定时收盘才带 `turso,neon`。
   `db-sync.yml` 的 `cancel-in-progress` 改为 `false`，防止刚采到的数据那次同步
   被后续定时同步取消。定时同步降级为纯兜底。
4. **发布链路不再被 Pages 抖动卡死**：`publish_ui.py` 的基线读取与 `gh` 调用加
   退避重试；静态金融数据早已迁到在线库，Pages 基线 `404` / 持续 `5xx` 时降级为
   warning 并跳过逐字节比对（真正读到且不一致仍 fail-closed）。新增
   `test_publish_ui.py` 8 项回归。
5. **修掉「每轮采集后必然短暂误报」**：`fresh_until` 是行情源 20 分钟时效口径，
   而生产采集是盘中 30 分钟一次，直接用它判横幅会在 `14:53~15:03` 这类窗口
   必然弹出「行情更新超时」。新增展示层专用 `DSH.quoteStaleForDisplay()`，
   盘中快照给 45 分钟宽限（30 分钟节奏 + 15 分钟排队容错），收盘版仍按
   `fresh_until` 严格判定。`DSH.quoteFreshness` 业务口径一字未改，净值依赖 /
   `todayUnavailable` 等判断不受影响。

6. **盘中「本应秒退」却天天变红**：`live_strategy.run_equity()` /
   `live_ranking.run()` 原先第一行就是严格的 `load_snapshot()`，报价核验
   （`watchdog_checks.quote_problems`）在 `run_guard.should_skip()` **之前**执行。
   生产采集是 30 分钟一次，而心跳阈值是 15 分钟，于是「报价刷新任务超过
   15 分钟未成功」必然命中，作业还没走到「盘中快照不重算净值」就抛错，
   `在线净值与动态排名` 每次盘中触发都是红色 failure。现在先用
   `load_snapshot(strict=False)` 轻量取 payload 让 run-guard 秒退，
   **真要写净值（收盘场次）时再严格复核报价时效**，fail-closed 门禁一字未松。
   新增 `test_intraday_skip.py` 4 项锁定调用顺序与「收盘仍严格」两条边界。

**关于 `freeze` 档（不是故障，是刻意保护）**：本周期 `estimated_mb≈20417`
/ `budget_mb=3000`，`egress_budget` 判 `freeze`，盘中非关键刷新一律跳过
（`allow=false`），跑出来是 `skipped` 而非 `failure`。关键任务带
`--critical` 仍放行，`workflow_dispatch` 补采有 `TRADE_FORCE_BUDGET=1`
强制放行 —— 所以收盘 / 开盘 / 自愈补采三条链路不会因超额而断。
这是「已超额就不再做无意义的盘中重复刷新」的额度策略，不是流水线停摆。

**回归**：Python `296` 项全绿（新增 `test_reconcile_sessions` 20 项、
`test_publish_ui` 8 项、`test_intraday_skip` 4 项）、Node `43` 项全绿、
工作流 YAML `24` 份解析通过、`trading_window` 自检 `15` 项 +
`reconcile_sessions` 自检 `13` 项全 OK。

**边界（不夸大）**：GitHub cron 仍不保证字面准点，本版也不承诺「某分某秒必跑」。
可靠性来自「任意一次运行都对账 → 缺什么补什么 → 幂等去重 → 失败自动重试」，
即使一整天的 schedule 全被丢弃，只要有一次运行到达（或独立兜底 cron 到达），
缺口就会被补齐。另：`collect-full.yml` / `collect-ci.yml` / `backfill-prices.yml`
是**历史数据回填**链路，分别因 Yahoo 补缺未完成、`HTTP 402` 付费墙、
Alpha Vantage 免费 25 次/日限流而周期性失败，与日更链路无关，不绕过往返门禁、
不伪造历史价格（如需消除这些红色失败可另行降频或改手动）。

## v6.9 ｜ 2026-11-10 ｜ 手动派发脏数据防护、自愈分时补跑、开盘即同步

**背景**：v6.8 修掉了「GitHub 延迟 / freeze 拦截 / 同步早于采集 / job 超时」四个断点后，
11/09 的收盘数据仍无法补回（在线挂牌只保留最近一个场次，盘前 `gb_spy` 会把前收价
写成现价、涨跌额置 0）。页面因此仍显示「截至 11/06」+「行情更新超时」。本版把
**「开盘后 30 分钟」与「每日收盘」两次关键采集**剩下的三个结构性漏洞补齐。

**本版六处修复**

1. **手动派发不再无条件绕过日历门禁**。`quotes.yml` 的 `workflow_dispatch` 分两种：
   带 `as_of` 是看门狗自愈的延迟补跑（逻辑时间由 `live_quotes.logical_time` 用
   20h 上限 / NYSE 日历场次 / 收盘后窗口三重校验），按 `closing --late-ok` 放行；
   **不带 `as_of` 的人工实时验证改借 `intraday` 日历窗口裁决**（`GATE_EVENT=schedule`）。
   实测盘前新浪三字段自洽但语义是假的（`p=pc=752.69`、`chg=0`），原先放行会把整轮
   假报价写进生产并污染净值。非交易时段强制验证仍可用 `TRADE_FORCE_COLLECT=1`。
2. **自愈按所处时段选补跑方式**。`selfheal.dispatch_args()` 原先无条件带
   `as_of=上一交易日收盘后 17 分钟`：盘中派发时逻辑时间被固定到昨日，而在线报价
   已是今日时间戳，`source_time` 判 `Future source quote`，必然失败，形成
   「告警 → 派发 → 再告警」的无效循环。改为：盘中抓实时价不带 `as_of`；
   收盘后 / 次日凌晨用 `closing_as_of()` 补最近一次收盘（20h 内）；
   当日盘前不派发，交给开盘关键 cron。所有行情补跑仍带 `critical=true`。
3. **开盘采集成功后立即推 Turso**。原先「采集成功即同步」只对 `closing` 生效，
   开盘那次只在主库落地，访客（读 Turso）要等下一次 30 分钟定时同步才看到。
   现在 `opening` 成功后立即派发 `db-sync.yml -f targets=turso`，
   `closing` 才派发 `turso,neon`（Neon 每工作日只唤醒一次的额度约束不变）。
4. **自愈 / 人工补采成功后也必须立即同步**。第 3 点初版只放行 `opening`/`closing`
   两种 schedule 任务；看门狗派发的 `workflow_dispatch` 走 `intraday` 任务，
   会出现「主库快照已更新、Turso 仍旧、页面继续告警、自愈反复重采」的断链。
   现在同步条件加上 `github.event_name == 'workflow_dispatch'`，且只有
   **定时收盘**（`TASK=closing && EVENT=schedule`）才推 `turso,neon`，
   盘中补采只推 Turso，绝不误唤醒 Neon。
5. **看门狗不再把盘中「净值版本落后」判为故障**。`watchdog_site_check` 调用
   `published_dependency_problems()` 时，盘中快照的 `equity`/`preview` 因
   `run-guard` 明确「净值/预览只在收盘场次计算」必然落后于刚写入的盘中报价，
   于是 A/B 两组共 4 条 problem → 每小时告警 + 开 Issue + 派发必定被 SKIP 的
   `live-strategy.yml` 空转。现在 `quotes.intraday=True` 时把这两类「版本落后」
   降级（其它依赖错误仍告警），收盘场次 `intraday=False` 照常严格校验——
   那时净值没跟上就是真故障。新增盘中/收盘正反两组回归。
6. **看门狗增加「盘中当日快照缺失」早发现**。实测 GitHub 免费账户的
   scheduled 事件会整批延迟甚至整点不触发：2026-11-10 15:00 UTC 的
   `opening` cron 与 `*/30 13-20` 盘中 cron 到 15:04 都没有产生任何 run。
   原先只看「收盘后 90 分钟」与 72 小时阈值，会让开盘到收盘这大半天失明。
   现在交易时段内（开盘后 35 分钟宽限 ~ 收盘）若 `quotes.session` 不是当日，
   立即报「行情停更：… 盘中快照缺失」，`selfheal` 派发 `quotes.yml` 盘中实时
   补采，补采成功后立即同步 Turso——**闭环不再依赖 cron 是否准时**。
   新增 3 项回归（缺失早发现 / 当日已到位不误报 / 开盘宽限不误报）。

**平台级限制（如实记录）**：GitHub Actions 免费层的 scheduled 事件延迟/整批
投递无法在本仓库内消除。因此「按字面时刻 100% 准时」不能由 cron 单独保证；
本版的可靠性来自「多关键时刻 + 延迟补跑 `as_of` + 盘中早发现 + 自愈补采 +
看门狗 + 采集成功即同步」的多层冗余，保证的是**数据不丢、页面不中断**。
若要求严格准点，需引入外部触发源（第三方 cron → `repository_dispatch`），
这需要另行授权与凭据，本版没有擅自接入。

## v6.8 ｜ 2026-11-10 ｜ 关键采集自愈闭环、身份裁定入库、读源自动降级

**线上症状**：移动端顶部「行情更新超时」、主卡片「建议待更新」、收益「截至 11/06」。Turso 14 个 key 全部停在 11/05~11/06，11/09 周一整天数据一次都没采到。

**四个串联断点（实测，非推测）**

1. GitHub scheduled 事件大幅延迟：`50 21 * * 1-5`（计划 UTC 21:50）实际 11/10 03:49 UTC 才跑；`trading_window` 按**实际执行时刻**判定，输出 `已收盘 410 分钟，超出 closing 采集窗口` → `allow=false`。
2. 看门狗确实检测到 `行情停更 84.6 小时` 并派发了 `quotes.yml` 自愈补跑（run `42792327630`），但该 dispatch 没有 `--critical`，`egress_budget.py` 处于 `freeze` 档（`19784.7 / 3000 MB`）→ `allow=false` → 采集步骤 skipped。
3. `db-sync.yml` 收盘同步在 **21:10 UTC**，比 `quotes.yml` 的 **21:17** 收盘采集还早，同步的永远是前一天数据。
4. 采集 job 只有 `timeout-minutes: 4`；500+ 标的分批抓取 + 缺失报价佐证修复实测跑到 4 分钟被硬砍（两次补采都在采集途中 `canceled`）。

**修复（勿回退）**

## v6.5 ｜ 2026-11-08 ｜ 访客提示语义治理：冗余切换不再误报故障

**问题**：移动端顶部常驻红条「主数据库暂不可用，已自动切换到备用数据库（turso）」。主库免费额度耗尽返回 402、浏览器自动改读 Turso 实时备库，是设计内的计划路径，但页面把「用了哪个端点」直接当成「是否故障」，于是每次正常访问都弹故障告警。

**根因（三处）**
- `DSH.dataStatus()` 只按 `activeType === "turso"` 得出 `mode=backup`，`showSourceNotice()` 据此无条件建红色横幅；`degraded` 又是「曾经失败过」的残留标记，未随恢复清理。

**设计口径（勿回退）**：**冗余对访客应当无感**。端点类型只是路由诊断信息，不构成访客可见状态；唯一依据是数据健康度。

- `app.js` 新增 `level`（`healthy` / `degraded` / `offline`）与统一提示状态中心 `reportNotice` / `clearNotice` / `renderNotices`；`mode` 保留为诊断用的路由快照。所有来源共用一个 `#serviceBanner`，任一来源恢复即重算并自动移除；`health` 这类辅助 key 取不到不再把整页判为离线。
- `page.js` 删除 `showSourceNotice()`，改为单一 `renderServiceNotice()`：核心数据缺失（`error`）、行情停更与云端健康异常（`warn`）、全部端点不可用且只能展示最近缓存（`info`）才提示；正常态零横幅。页脚不再标注「备用数据库」，仅真用缓存时标注「最近缓存」。
- `dashboard.css` 新增 `.data-notice` 中性蓝灰样式，非故障告知不再借用红色告警色。
- `402/429/5xx` 熔断带过期时间写入 `localStorage`，成功即清除：额度耗尽期间跨刷新不再重复撞主库，也不永久锁死主库。
- 顺手把 `health` 检查改为显式 `window.DSH`，不再依赖「window 属性自动成为全局变量」的隐式行为（严格模式/模块化/测试沙箱一致）。

**回归**：Node 40 项（新增 10 项覆盖「备库健康零提示 / 真实异常仍告警 / 恢复后清除 / 熔断跨刷新 / 旧文案退场」）；Python 189 项、CI 门禁 50 项、22 个 YAML 全绿；`verify_replication.py` `PROBLEMS=0`；线上 E2E 失败 0；`failover_drill.mjs --online` 仍 `FAILOVER_DRILL_OK`。
